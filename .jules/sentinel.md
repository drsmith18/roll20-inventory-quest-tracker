## 2024-05-18 - Client-Side API Boundaries versus UI Boundaries in Roll20 Extensions
**Vulnerability:** Authorization bypass. The `deleteBag` and `wipeAll` methods in `PT.store` (used by the Roll20 extension) were intended to be DM-only. The UI correctly hid the buttons for these actions from players, but the underlying API functions themselves lacked validation to check if the caller was actually the GM. Additionally, a parameter injection vulnerability was found in `drops.js` where `expansionId` was not encoded before being appended to a URL.
**Learning:** Hiding UI elements is not a substitute for authorization checks in the underlying API methods, especially in a client-side context where any user can open the console and invoke the globally exposed functions directly. The fact that the extension relies on Roll20's Firebase backend, which players might have write access to (for their own handouts/bags), makes verifying the GM role (`env.isGM` or `window.is_gm`) directly inside the API methods critical.
**Prevention:** Always enforce authorization at the lowest possible level in the API/service layer, not just in the presentation layer. Ensure all user-supplied data used in URLs or queries is properly encoded or sanitized.
